# AGENTS.md

## 1. О проекте (Project Overview)

Weezzy - backend для внутреннего ITMO-сервиса нетворкинга, общения и поиска людей
в команду. По смыслу это не классический dating app, а платформа, где студент может
создать профиль, указать скиллы, интересы и цели, получать рекомендации людей,
голосовать за анкеты и получать матч при взаимном `LIKE`.

Основные возможности: auth с подтверждением email и refresh rotation, профили с
фотографиями и signals, рекомендации, votes/matches/blocks, moderation,
in-app уведомления и email решений о санкциях через outbox, экспресс-обеды,
команды с позициями, объявлениями о наборе, приглашениями и откликами.
Onboarding контролирует активацию профиля. При удалении аккаунта персональные
данные удаляются, а обезличенный профиль сохраняется для целостности истории.

Проект сейчас является backend-only приложением. Фронта и мобильного приложения в
репозитории пока нет.

## 2. Технологический стек (Tech Stack)

- Java 21, Spring Boot 4.1, Gradle Kotlin DSL;
- Spring MVC, Validation, Security, Data JPA/Hibernate;
- PostgreSQL 17/pgvector и Flyway;
- Redis для auth rate limiting и отзыва access-токенов;
- Spring Mail, AWS SDK и MinIO/S3-compatible storage;
- JUnit 5, Spring Boot Test, MockMvc и Testcontainers.

Локальная инфраструктура:

- `docker-compose.yml` поднимает PostgreSQL, Redis, pgAdmin и MinIO;
- PostgreSQL локально доступен на `localhost:5433`;
- Redis локально доступен на `localhost:6380`;
- pgAdmin локально доступен на `http://localhost:5050`.
- MinIO S3 API локально доступен на `http://localhost:9000`;
- MinIO Console локально доступна на `http://localhost:9001`.

Redis используется для rate limiting auth-операций и отзыва access-токенов.
Он не является хранилищем бизнес-данных. Не расширять его использование без явной
задачи.

## 3. Архитектура и структура (Project Structure)

Production-код находится в `src/main/java/ru/itmo/nemat/weezzy`, тесты — в
`src/test/java`, конфигурация — в `src/main/resources`, Flyway SQL — в
`src/main/resources/db/migration`.

Ключевые домены: `user/security`, `profile/onboarding`, каталоги signals,
`recommendation`, `connection`, `team`, `location/lunch`, `moderation`,
`notification/outbox`, `storage` и `common`.

Архитектурный стиль:

- package-by-domain, а не раздельные глобальные пакеты `controller/service/repository`;
- внутри домена обычно есть `Entity`, `Repository`, `Service`, `Controller`, `dto`;
- для вложенных сущностей используются подпакеты, например `profile.skill`;
- контроллеры тонкие: HTTP, DTO, получение authenticated user, вызов service;
- бизнес-логика находится в service-классах;
- доступ к базе идет через Spring Data repositories;
- schema-first через Flyway: новые таблицы/индексы добавлять миграциями;
- Hibernate `ddl-auto=validate`, поэтому entity обязаны совпадать с миграциями;
- все user-owned действия должны брать user/profile из JWT, а не из request body.

## 4. Правила разработки и Code Style (Development Guidelines)

Java style:

- классы и records - `PascalCase`;
- методы, поля, переменные - `camelCase`;
- enum constants - `UPPER_SNAKE_CASE`;
- пакеты - lowercase, доменные: `skill.suggestion`, `connection.vote`;
- DTO records называются `CreateXRequest`, `UpdateXRequest`, `XResponse`;
- exception-классы называются по смыслу: `DuplicateSkillException`,
  `ProfileNotFoundException`;
- использовать constructor injection через `final` fields и Lombok
  `@RequiredArgsConstructor`;
- entity сейчас обычно используют Lombok `@Data`;
- даты в текущем проекте держать в `LocalDateTime`, чтобы не плодить разные типы;
- строки желательно держать до 85-90 символов, если это не ухудшает читаемость;
- не делать масштабный рефакторинг структуры без отдельного решения.

Spring/JPA rules:

- write operations помечать `@Transactional`;
- read-only operations помечать `@Transactional(readOnly = true)`;
- связи entity оформлять явно: `@ManyToOne`, `@OneToOne`, `@JoinColumn`;
- для many-to-many связей сейчас используются отдельные join entity:
  `ProfileSkill`, `ProfileInterest`, `ProfileGoal`;
- composite keys оформлены через id-классы (`ProfileVoteId`, `ProfileMatchId`);
- не полагаться на Hibernate auto-DDL, все изменения схемы делать через Flyway;
- для новых lookup/search полей сразу думать про индекс.

Security rules:

- без JWT доступны register, login, refresh, подтверждение/повторная отправка email,
  восстановление пароля, health probes и Swagger/OpenAPI; точный список задан в
  `SecurityConfig`;
- остальные endpoints требуют authentication;
- текущий user берется через `@AuthenticationPrincipal JwtAuthenticatedUser`;
- user-owned endpoints должны быть вида `/me`, например `/api/profiles/me`;
- не принимать `userId` или `sourceProfileId` из body/path там, где это текущий user;
- endpoints под `/api/admin/**` требуют роль `ADMIN`; отдельные операции управления
  каталогами вне этого префикса также требуют `ADMIN`, согласно `SecurityConfig`.

Error handling:

- использовать кастомные exceptions, наследованные от:
  `NotFoundException`, `ConflictException`, `BadRequestException`,
  `ForbiddenException`;
- не кидать голый `RuntimeException` для ожидаемых бизнес-ошибок;
- HTTP errors централизованы в `ApiExceptionHandler`;
- validation errors идут через Bean Validation annotations и возвращают `400`;
- duplicates обычно возвращают `409 Conflict`;
- missing entities обычно возвращают `404 Not Found`.

Testing rules:

- для controller/integration tests использовать `@SpringBootTest` + `@AutoConfigureMockMvc`;
- для БД использовать Testcontainers PostgreSQL;
- helper `AuthenticatedTestUser` использовать для регистрации тестового user,
  получения JWT и авторизации MockMvc-запросов;
- тесты должны проверять happy path, validation, auth required, not found/conflict;
- при изменении security обязательно добавлять/обновлять проверки `401`;
- при изменении миграций запускать полный `.\gradlew.bat test`;
- полный тестовый прогон требует запущенный Docker Desktop.

Команды:

```powershell
docker compose up -d
.\gradlew.bat bootRun
.\gradlew.bat compileTestJava --console=plain
.\gradlew.bat test --rerun-tasks --console=plain
```

## 6. Актуальный snapshot backend

### Экспресс-обеды

- MVP закрыт: заявки, matching, продления, lifecycle групп, временный REST-чат
  и cleanup работают. Не дублировать этот flow новыми задачами.
- Matching: точная корзина `location_id + time_slot`, группы по 3–4 человека,
  менее чем за 5 минут допустимы пары. Соседние слоты — только после согласия
  на продление. Совместимость, санкции и blocks перепроверяются в транзакции.
- Фоновые операции идемпотентны: advisory lock для корзин, `SKIP LOCKED` для
  lifecycle/cleanup; события идут через transactional outbox.
  Системная отмена сохраняет membership, eligible-заявки возвращает в SEARCHING,
  остальные переводит в EXPIRED.
- `/api/lunch/groups/me` и `/messages` доступны current membership ACTIVE группы.
  Чат: POST идемпотентен по clientMessageId, GET использует before/after,
  сообщения идут хронологически. После COMPLETED/CANCELLED чат недоступен.
- Контакты не раскрываются. После встречи используется обычный LIKE и ProfileMatch.
  Параметры — `app.lunch`, retention/cleanup — `app.lunch.chat`.
  Воркеры публикуют Micrometer метрики; гонки и cleanup покрыты интеграционными тестами.

### Команды, позиции и набор

- Команда имеет обязательную текстовую цель `Team.purpose`.
  Создание атомарно добавляет автора из JWT владельцем и участником:
  `ownerPositionName` задаёт его занятую позицию capacity=1.
- `TeamPosition` принадлежит команде: название, описание, capacity и Skill.
  Каждый участник обязан иметь одну позицию своей команды, включая основателя.
  Это обеспечено и схемой БД. Права владельца не заменяют профессиональную роль.
- Позиции можно создавать, читать и редактировать через
  `/api/teams/{teamId}/positions`. Изменения — владельцу активной команды
  с активным профилем; capacity нельзя уменьшить ниже занятого количества.
- `TeamRequest` — объявление; `TeamRequestPosition` связывает его с существующей
  позицией команды. Несколько объявлений могут публиковать одну позицию.
  Ссылка остаётся после заполнения; свободные места вычисляются по участникам.
- Объявления: создание и список владельца — `/api/teams/{teamId}/requests[/me]`;
  карточка/редактирование — `/api/team-requests/{requestId}`, закрытие — `/close`.
  Редактируются title/description/deadline, ссылки на позиции сохраняются.
  Закрытие идемпотентно и не удаляет позиции/состав; дедлайн сам статус не меняет.
- Поиск `GET /api/team-requests`: query до 200 символов, skillIds до 20,
  sort=NEWEST/DEADLINE_ASC, page/size. Текст ищется без учёта регистра в объявлении,
  названии/цели команды и свободной позиции; LIKE-символы экранируются.
  Текст позиции и все искомые навыки должны совпасть на одной свободной позиции.
- Поиск возвращает OPEN объявления с будущим дедлайном и местами, исключая свои
  команды. Общий TeamVisibility учитывает активность команды/владельца, аккаунт,
  членство владельца, санкции и blocks. Фильтрация/count — в БД до пагинации.
  Подстроковый поиск пока без отдельного индекса.
- `TeamInvitation` адресуется позиции команды: inviteeProfileId + positionId.
  Создаёт владелец, принимает/отклоняет получатель, отменяет отправитель.
  Входящие — `/api/team-invitations/me`, по умолчанию доступные PENDING.
- `TeamApplication` — отклик на позицию объявления. Автор отправляет/отзывает,
  владелец принимает/отклоняет. API и DTO: `docs/team-applications.md`.
  positionId отклика — ID TeamRequestPosition; teamPositionId — ID TeamPosition.
- Оба принятия используют `TeamMemberService.ensureCanJoin/add`: проверяются
  активность, санкции, blocks владельца/кандидата, отсутствие участия и место.
  Отклик дополнительно требует OPEN объявления с будущим дедлайном.
  Участник с позицией, решение и outbox сохраняются атомарно.
  Повтор того же решения идемпотентен; другое решение возвращает conflict.
- Вместимость общая для всех объявлений, приглашений и откликов позиции.
  PENDING не резервирует места. Выход/исключение освобождает место;
  повтор старого ACCEPTED не восстанавливает участие.
- Порядок блокировок: accounts по ID, profiles по ID, team, затем
  request/application либо invitation. Изменение capacity тоже блокирует team.
  Использовать TeamAccessService, ProfileService, AccountProfileLockService,
  TeamPositionService и TeamRequestService; не обращаться из команд к ProfileRepository.
- Выход/исключение: DELETE `/api/teams/{teamId}/members/me` или `/{profileId}`.
  Владелец не удаляет себя. Blocks/неактивный профиль не мешают, санкции действуют.
  Исключение отменяет pending приглашения кандидату.
- Архивирование `POST /api/teams/{teamId}/archive` идемпотентно, сохраняет историю
  и состав, отменяет pending приглашения, запрещает вступления/изменения.
  Отзыв/отклонение отклика доступны после закрытия, дедлайна и архива.
  Владелец может читать историю/закрывать объявления при неактивном профиле
  или архивной команде, если его аккаунт не под санкциями.
- Карточки показывают доступных участников и их позиции, без Telegram/email/user ID.
  Уведомления приглашений/откликов идут через outbox с дедупликацией и проверкой
  доступности/актуальности. Решения могут доставляться после закрытия/дедлайна,
  отклонение и отзыв — после архива; payload без контактов.

### Санкции и проверки

- HMAC нормализованного email сохраняется в санкции и препятствует обходу бана
  через удаление/регистрацию. Production требует стабильный SANCTION_EMAIL_HMAC_KEY
  от 32 байт; замена ломает поиск старых fingerprints.
- Email назначения/отзыва санкций: outbox, SMTP в production, логирование local,
  retry при ошибках, пропуск удалённых адресатов. In-app inbox при бане недоступен.
  Реальный production SMTP ещё не проверен; exactly-once доставки не обещать.
- Последний полный прогон: 996 тестов, без ошибок и пропусков
  (2026-11-17, финал этапа 14 рекомендаций команд). Нагрузочный volumeTest
  (тег volume) исключён из `test` и запускается `.\gradlew.bat volumeTest`.
  Покрыты API, миграции, rollback/outbox, вместимость и конкурентные вступления.
  Тестовой JVM выделен heap 1 ГБ. Тесты запускать после логического блока,
  при миграциях — полный suite.

### Отбор, ранжирование и карточка

- Рекомендуем человеку команды через их объявления TeamRequest. Подбор кандидатов
  владельцу — отдельная будущая задача. Использовать существующие правила
  видимости: OPEN, будущий дедлайн, свободные места, санкции/blocks, исключение
  команд, где пользователь уже участник.
- Навыки сравниваются по общему Skill: ProfileSkill и TeamPositionSkill.
  Базовый порядок: число совпадений по убыванию, затем доля навыков позиции,
  покрытая профилем. Лишние навыки профиля не штрафуются.
  Пустой набор навыков — недостаток данных, не полное совпадение.
- Это мягкое ранжирование: после подходящих выдавать доступные варианты с нулём
  совпадений/без навыков. Не заканчивать ленту только из-за низкой оценки.
  Нет обязательного порога навыков для отклика и процентов «совместимости».
- Одна команда — одна запись в сессии ленты, независимо от числа объявлений.
  Объединять доступные позиции открытых объявлений команды, без повторов одной
  TeamPosition. Для каждой опции сохранять связь с конкретным TeamRequestPosition
  для существующего API отклика.
- Главная позиция — лучшая по совпадению навыков среди свободных доступных опций.
  Число позиций/объявлений и количество мест сами по себе не дают бонуса.
  Пользователь может выбрать другую позицию карточки.
- Объяснение: рекомендуемая позиция, совпавшие и остальные указанные навыки.
  Карточка содержит команду/цель, позиции и доступных участников
  (profileId, имя, фото, позиция) для перехода в профиль, без контактных данных.
- Существующий путь: выбор позиции → TeamApplication → одобрение владельцем →
  TeamMemberService → участник на выбранной позиции. Новый механизм вступления
  не создавать. Место повторно проверяется при отклике и принятии.
- PENDING отклик исключает повторное предложение откликнуться на ту же позицию
  команды, в том числе через другое объявление; другие позиции могут остаться.
  Это правило рекомендаций, не молчаливое изменение общего API откликов.
- После DECLINED на ту же TeamPosition действует жёсткий запрет повторного
  отклика 24 часа от последнего отказа, через любое объявление. Проверять и в
  рекомендациях, и в существующем TeamApplicationService.send (409).
  Другие позиции команды, прямые приглашения и существующие PENDING не блокировать.
  WITHDRAWN не создаёт/не сбрасывает запрет; повтор decline не продлевает его.
- LIKE/PASS, скрытия и избранное в MVP не входят. Можно листать без решения.
  Названия ролей и Team.purpose — свободный текст: без enum ролей,
  семантического сопоставления целей и обучаемой модели на этом этапе.

### Сессия, возврат назад и cooldown

- Сессия ленты хранится на сервере в PostgreSQL: владелец, ID, упорядоченные
  ссылки на команды. Не хранить копии медиа/всех карточек и не расширять Redis.
  Порядок устойчив в рамках сессии; обновление подборки создаёт новую сессию.
- Курсорная пагинация в обе стороны: nextCursor/previousCursor привязаны
  к сессии и позиции в ней. Клиент держит положение и ограниченный кеш страниц;
  выгруженные страницы может повторно получить с сервера до истечения сессии.
- «Один раз в ленте» запрещает дубли записей, но не возврат к старой карточке.
  Открытие профиля участника и возвращение не должны сбрасывать положение.
  Cooldown не запрещает чтение уже выданной страницы.
- Порядок фиксирован, данные и доступность актуальны: повторно проверять
  видимость, санкции/blocks, статус объявлений и места. Сессия не даёт доступ
  к ставшим недоступными данным и не гарантирует наличие места.
- История просмотров отделена от сессии. Учитывать фактическое появление карточки
  на экране, не предзагрузку; идемпотентно один просмотр команды за сессию.
  Листание назад не продлевает cooldown многократно.
- Cooldown мягкий и настраиваемый: в новой подборке сначала команды вне cooldown,
  включая нулевые совпадения; после их исчерпания — команды внутри cooldown,
  начиная с наиболее давно показанных. В одной сессии повторов всё равно нет.
  Пустая/исчерпанная выдача допустима, когда доступные уникальные варианты закончились.

### Решения прохода 1

- Мягкий cooldown показов — 3 дня, TTL сессии — 24 часа, история — 30 дней.
  Запрет повторного отклика после отказа — отдельные жёсткие 24 часа на позицию.
- POST/GET сессий и POST impressions: /api/team-recommendations/me/sessions.
  Полные DTO, примеры, ошибки, ограничения и критерии показа описаны в контракте.
- Порядок всех подходящих ID фиксируется целиком; pageSize 20 (1–50) постоянен.
  Окна страниц не сдвигаются: недоступные карточки пропускаются, включая целые
  пустые окна. Клиент продолжает по next/previousCursor до null.
- Данные/объяснения актуальны, порядок команд прежний. Новые команды — только
  в новой сессии. Для повторяющейся позиции выбирается объявление с ближайшим
  будущим дедлайном. Карточку без допустимых опций не возвращать.
- POST создания имеет clientRequestId для сетевых повторов. Максимум 10 активных
  сессий, новая вытесняет старую; истёкшая/чужая/удалённая сессия возвращает 404.
  Стоимость полного снимка измерена на этапе 14: 3000 команд — ~0,8 с создание,
  ~268 байт на запись; цифры и ограничения — в контракте.

  публикация выбирается по ближайшему дедлайну, затем новизне и UUID.
  Главная позиция/объяснения пересчитываются по текущим навыкам. Недоступные

  по 500; графы карточек не загружаются. Создание не фиксирует выдачу или показ.
  История пользователя читается для доступных команд порциями до 500 ID.

  Показ и повтор clientRequestId не меняют порядок существующей сессии.
- TeamRecommendationPageService читает фиксированное окно до 50 entries,
