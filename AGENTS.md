# AGENTS.md

## 1. О проекте (Project Overview)

Weezzy - backend для внутреннего ITMO-сервиса нетворкинга, общения и поиска людей
в команду. По смыслу это не классический dating app, а платформа, где студент может
создать профиль, указать скиллы, интересы и цели, получать рекомендации людей,
голосовать за анкеты и получать матч при взаимном `LIKE`.

Основные возможности: auth с подтверждением email и refresh rotation, профили с
фотографиями и signals, рекомендации, votes/matches/blocks, moderation,
in-app уведомления и email решений о санкциях через outbox, экспресс-обеды.
Onboarding контролирует активацию
профиля. При удалении аккаунта персональные данные удаляются, а обезличенный
профиль сохраняется для целостности истории.

Проект сейчас является backend-only приложением. Фронта и мобильного приложения в
репозитории пока нет.

## 2. Технологический стек (Tech Stack)

- Java 21, Spring Boot 4.1, Gradle Kotlin DSL;
- Spring MVC, Validation, Security, Data JPA/Hibernate;
- PostgreSQL 17/pgvector и Flyway;
- Redis для auth rate limiting и отзыва access-токенов;
- Spring Mail, AWS SDK и MinIO/S3-compatible storage;
- JUnit 5, Spring Boot Test, MockMvc и Testcontainers.

Локальная инфраструктура:

- `docker-compose.yml` поднимает PostgreSQL, Redis, pgAdmin и MinIO;
- PostgreSQL локально доступен на `localhost:5433`;
- Redis локально доступен на `localhost:6380`;
- pgAdmin локально доступен на `http://localhost:5050`.
- MinIO S3 API локально доступен на `http://localhost:9000`;
- MinIO Console локально доступна на `http://localhost:9001`.

Redis используется для rate limiting auth-операций и отзыва access-токенов.
Он не является хранилищем бизнес-данных. Не расширять его использование без явной
задачи.

## 3. Архитектура и структура (Project Structure)

Production-код находится в `src/main/java/ru/itmo/nemat/weezzy`, тесты — в
`src/test/java`, конфигурация — в `src/main/resources`, Flyway SQL — в
`src/main/resources/db/migration`.

Ключевые домены: `user/security`, `profile/onboarding`, каталоги signals,
`recommendation`, `connection`, `location/lunch`, `moderation`,
`notification/outbox`, `storage` и `common`.

Архитектурный стиль:

- package-by-domain, а не раздельные глобальные пакеты `controller/service/repository`;
- внутри домена обычно есть `Entity`, `Repository`, `Service`, `Controller`, `dto`;
- для вложенных сущностей используются подпакеты, например `profile.skill`;
- контроллеры тонкие: HTTP, DTO, получение authenticated user, вызов service;
- бизнес-логика находится в service-классах;
- доступ к базе идет через Spring Data repositories;
- schema-first через Flyway: новые таблицы/индексы добавлять миграциями;
- Hibernate `ddl-auto=validate`, поэтому entity обязаны совпадать с миграциями;
- все user-owned действия должны брать user/profile из JWT, а не из request body.

## 4. Правила разработки и Code Style (Development Guidelines)

Java style:

- классы и records - `PascalCase`;
- методы, поля, переменные - `camelCase`;
- enum constants - `UPPER_SNAKE_CASE`;
- пакеты - lowercase, доменные: `skill.suggestion`, `connection.vote`;
- DTO records называются `CreateXRequest`, `UpdateXRequest`, `XResponse`;
- exception-классы называются по смыслу: `DuplicateSkillException`,
  `ProfileNotFoundException`;
- использовать constructor injection через `final` fields и Lombok
  `@RequiredArgsConstructor`;
- entity сейчас обычно используют Lombok `@Data`;
- даты в текущем проекте держать в `LocalDateTime`, чтобы не плодить разные типы;
- строки желательно держать до 85-90 символов, если это не ухудшает читаемость;
- не делать масштабный рефакторинг структуры без отдельного решения.

Spring/JPA rules:

- write operations помечать `@Transactional`;
- read-only operations помечать `@Transactional(readOnly = true)`;
- связи entity оформлять явно: `@ManyToOne`, `@OneToOne`, `@JoinColumn`;
- для many-to-many связей сейчас используются отдельные join entity:
  `ProfileSkill`, `ProfileInterest`, `ProfileGoal`;
- composite keys оформлены через id-классы (`ProfileVoteId`, `ProfileMatchId`);
- не полагаться на Hibernate auto-DDL, все изменения схемы делать через Flyway;
- для новых lookup/search полей сразу думать про индекс.

Security rules:

- без JWT доступны register, login, refresh, подтверждение/повторная отправка email,
  восстановление пароля, health probes и Swagger/OpenAPI; точный список задан в
  `SecurityConfig`;
- остальные endpoints требуют authentication;
- текущий user берется через `@AuthenticationPrincipal JwtAuthenticatedUser`;
- user-owned endpoints должны быть вида `/me`, например `/api/profiles/me`;
- не принимать `userId` или `sourceProfileId` из body/path там, где это текущий user;
- endpoints под `/api/admin/**` требуют роль `ADMIN`; отдельные операции управления
  каталогами вне этого префикса также требуют `ADMIN`, согласно `SecurityConfig`.

Error handling:

- использовать кастомные exceptions, наследованные от:
  `NotFoundException`, `ConflictException`, `BadRequestException`,
  `ForbiddenException`;
- не кидать голый `RuntimeException` для ожидаемых бизнес-ошибок;
- HTTP errors централизованы в `ApiExceptionHandler`;
- validation errors идут через Bean Validation annotations и возвращают `400`;
- duplicates обычно возвращают `409 Conflict`;
- missing entities обычно возвращают `404 Not Found`.

Testing rules:

- для controller/integration tests использовать `@SpringBootTest` + `@AutoConfigureMockMvc`;
- для БД использовать Testcontainers PostgreSQL;
- helper `AuthenticatedTestUser` использовать для регистрации тестового user,
  получения JWT и авторизации MockMvc-запросов;
- тесты должны проверять happy path, validation, auth required, not found/conflict;
- при изменении security обязательно добавлять/обновлять проверки `401`;
- при изменении миграций запускать полный `.\gradlew.bat test`;
- полный тестовый прогон требует запущенный Docker Desktop.

Команды:

```powershell
docker compose up -d
.\gradlew.bat bootRun
.\gradlew.bat compileTestJava --console=plain
.\gradlew.bat test --rerun-tasks --console=plain
```

## 6. Текущий snapshot экспресс-обедов

- Заявки, matching pipeline, формирование групп, продления и lifecycle уже работают.
- Matching использует только точную корзину `location_id + time_slot`; соседние
  слоты объединяются только через подтверждённое пользователем продление.
- Группы формируются по 3–4 человека; менее чем за 5 минут допускаются аварийные
  пары. Совместимость, санкции и blocks повторно проверяются транзакционно.
- Все фоновые переходы конкурентно безопасны и идемпотентны. Корзины matching
  claim-ятся advisory lock, независимые lifecycle-строки — через `SKIP LOCKED`.
- Формирование, предложение продления и системная отмена публикуются через
  transactional outbox.
- Системная отмена сохраняет историю membership, возвращает eligible-заявки в
  `SEARCHING`, а невалидные переводит в `EXPIRED`.
- `GET /api/lunch/groups/me` доступен только участнику активной группы и не раскрывает
  Telegram.
- Временный REST-чат работает через `POST/GET /api/lunch/groups/me/messages`:
  отправка идемпотентна по `clientMessageId`, история использует cursor pagination
  `before/after`, сообщения возвращаются в хронологическом порядке.
- Чат доступен только current membership группы со статусом `ACTIVE`; после
  `COMPLETED`/`CANCELLED` чтение и отправка запрещены. Ответы не раскрывают Telegram,
  email, внутренний user ID и `clientMessageId`.
- Сообщения закрытых групп удаляются batch cleanup-воркером после настраиваемого
  retention. Cleanup использует `SKIP LOCKED`, безопасен для нескольких инстансов и
  публикует метрики запусков, ошибок, длительности и количества удалений.
- Chat send/lifecycle races, конкурентный cleanup, pagination и retention проверены
  интеграционными тестами на PostgreSQL. Полный Testcontainers suite проходит.
- Знакомство после ланча использует существующий connection flow: фронт открывает
  профиль участника по `profileId` и отправляет обычный `LIKE`. Взаимный выбор создаёт
  стандартный `ProfileMatch` и раскрывает Telegram; отдельный lunch contact flow не
  используется.
- Matching, request lifecycle, group lifecycle и chat cleanup публикуют Micrometer
  метрики запусков, ошибок, длительности и количества обработанных сущностей.
- Длительности окна, шага слотов, продления, ответа и активной группы задаются через
  `app.lunch`; retention и cleanup чата — через `app.lunch.chat`.

## 7. Актуальные backend-направления

- Текущий MVP экспресс-обедов со стороны backend закрыт. Новые задачи в этом домене
  должны расширять продуктовый сценарий, а не дублировать уже существующий flow
  заявок, групп, чата и обычного `LIKE` после встречи.
- Команда собирается под конкретную цель (проект, хакатон, соревнование),
  которая обязательна в `Team.purpose`. Постоянные общие чаты — отдельный будущий
  сценарий. Завершённую команду можно архивировать с сохранением истории.
- Создание команды добавляет автора из JWT владельцем и участником в одной
  транзакции. Запрос содержит `purpose` и `ownerPositionName`: основателю создаётся
  занятая позиция вместимостью 1. Права владельца не заменяют профессиональную роль.
- Позиции принадлежат команде: `team.position.TeamPosition` содержит название,
  описание, `capacity` и навыки из существующего `Skill`. У каждого участника,
  включая основателя, обязательная позиция своей команды. Карточка возвращает
  цель, позиции и позиции доступных участников, без Telegram, email и user ID.
- API позиций: `POST/GET /api/teams/{teamId}/positions`,
  `GET/PUT /api/teams/{teamId}/positions/{positionId}`. Изменения доступны
  владельцу активной команды с активным профилем. Вместимость нельзя опустить
  ниже занятого количества. Удаление позиций и перевод участников пока не реализованы.
- Приглашение обязательно адресовано позиции команды: тело содержит
  `inviteeProfileId` и `positionId`. Отправляет владелец, принимает/отклоняет
  получатель, отменяет отправитель. Входящие доступны через
  `/api/team-invitations/me` с пагинацией и статусом; по умолчанию доступные PENDING.
- `TeamRequest` — объявление о наборе на существующие позиции этой команды.
  Создание через `POST /api/teams/{teamId}/requests` принимает `positionIds`.
  `TeamRequestPosition` только связывает объявление и позицию команды.
  Несколько объявлений могут публиковать одну позицию; вместимость у неё общая.
  Отдельного `targetTeamSize` больше нет.
- Карточка объявления: `GET /api/team-requests/{requestId}`, список владельца:
  `GET /api/teams/{teamId}/requests/me`, редактирование title/description/deadline:
  `PUT /api/team-requests/{requestId}`, идемпотентное закрытие:
  `POST /api/team-requests/{requestId}/close`. Редактирование сохраняет ссылки
  на позиции. Изменения позиции команды отражаются во всех объявлениях.
- Посторонним доступны только OPEN объявления с будущим дедлайном видимой
  команды; учитываются статус владельца, санкции и blocks. Владелец читает
  историю и закрывает объявление при неактивном профиле или архивной команде,
  если аккаунт не под санкциями. Просроченные объявления автоматически
  не меняют статус. Закрытие объявления не удаляет позиции и состав.
- `team.application` поддерживает отклики через позицию объявления, отзыв автором,
  принятие/отклонение владельцем, карточку для сторон и списки с пагинацией.
  Контракт, endpoints и различие ID описаны в `docs/team-applications.md`.
  `positionId` отклика — ID записи в объявлении; `teamPositionId` — позиция команды.
- Приглашения и отклики используют общий `TeamMemberService.ensureCanJoin/add`:
  проверяются профили, санкции, blocks, отсутствие участия и свободное место.
  Отклик дополнительно требует открытого объявления с будущим дедлайном.
  Принятие атомарно сохраняет участника с позицией, решение и событие outbox.
  Повтор решения идемпотентен; другое решение после закрытия возвращает conflict.
- `filledSlotsCount` считается по текущим участникам позиции,
  `remainingSlotsCount = capacity - filledSlotsCount`.
  `availableTeamSlotsCount` объявления — сумма свободных мест его позиций.
  Ожидающие приглашения/отклики места не резервируют. Выход/исключение освобождают
  место; повтор старого принятия не восстанавливает участие.
- Порядок блокировок: accounts по ID, profiles по ID, team, затем
  request/application либо invitation. Изменение вместимости тоже блокирует
  команду. Разные объявления, приглашения и отклики конкурируют за общие места.
- Права и видимость команды проверяет `TeamAccessService`, профили —
  `ProfileService`, упорядоченные блокировки — `AccountProfileLockService`.
  Позиции обслуживает `TeamPositionService`, объявления — `TeamRequestService`.
  Прямой доступ к ProfileRepository из командных сервисов не используется.
- Выход: `DELETE /api/teams/{teamId}/members/me`, исключение владельцем:
  `DELETE /api/teams/{teamId}/members/{profileId}`. Владелец не может удалить себя.
  Исключение отзывает pending приглашения кандидату. Blocks/неактивный профиль
  не мешают выходу и исключению; санкции действующего аккаунта сохраняют силу.
- `POST /api/teams/{teamId}/archive` доступен владельцу и идемпотентен.
  Сохраняет состав и историю, отменяет pending приглашения через outbox,
  запрещает вступления и изменения состава/позиций. Отзыв и отклонение откликов
  доступны после закрытия объявления, дедлайна и архивирования.
- Новый отклик и отзыв уведомляют владельца, принятие/отклонение — кандидата.
  Приглашения и решения также используют transactional outbox. Уведомления
  идемпотентны по source event, проверяют доступность сторон и актуальность.
  Решения по откликам могут доставляться после закрытия/дедлайна; отклонение
  и отзыв — после архива. Payload содержит позиции без контактных данных.
- V49 переносит старые позиции и навыки в команду, сохраняет ID и историю,
  делает позиции участников/приглашений обязательными и удаляет target_team_size.
  Старым участникам без позиции и приглашениям назначается техническая позиция
  «Позиция не указана (перенос)». Старые цели берутся из описания либо названия.
  Составные FK запрещают участникам и приглашениям позиции другой команды.
- Поиск объявлений: `GET /api/team-requests` с `query` (до 200 символов),
  `skillIds` (до 20), `sort=NEWEST/DEADLINE_ASC`, `page/size`.
  Подстрока без учёта регистра ищется в объявлении, названии/цели команды
  и свободной позиции; специальные LIKE-символы экранируются. Все навыки должны
  совпасть в одной свободной позиции. Текст позиции и навыки тоже проверяются
  на одной позиции. Пустой текст не ограничивает выдачу.
- Поиск показывает только OPEN объявления с будущим дедлайном и свободными местами,
  исключая команды читателя. Общий `TeamVisibility` используется поиском и карточкой:
  активные команда/владелец, аккаунт и членство владельца, санкции и blocks.
  Фильтрация и count выполняются в БД до пагинации, без дублей от позиций.
  V50 добавляет индекс новых OPEN объявлений; подстроковый текстовый поиск
  пока без отдельного индекса. Формат ответа — существующий TeamRequestResponse.
  После V50 полный прогон прошёл: 686 тестов, 0 ошибок и пропусков, включая
  32 новых API-теста поиска. До полного прогона целевые 96 тестов поиска,
  карточек команд и объявлений также прошли.
- Рекомендации объявлений/кандидатов пока не реализованы. Структурированные типы
  целей, список своих команд и редактирование карточки команды — отдельные
  следующие задачи. Обязательная текстовая цель уже реализована.
- Проверки покрывают API, роли основателя, вместимость, миграцию V48 → V49,
  rollback, outbox, гонки между объявлениями/приглашениями/откликами, закрытие,
  архивирование, blocks и санкции. Полный suite запускается после логического
  блока. После V50 полный прогон прошёл: 686 тестов, 0 ошибок и пропусков,
  включая 261 проверку команд. Тестовой JVM выделен heap 1 ГБ через
  `maxHeapSize` в Gradle.
- Обход санкций через удаление аккаунта и повторную регистрацию на тот же email
  закрыт: HMAC fingerprint нормализованного email сохраняется в санкции. Постоянный
  бан блокирует регистрацию до отзыва, временный — до истечения или отзыва.
  Production требует стабильный `SANCTION_EMAIL_HMAC_KEY` длиной от 32 байт;
  замена ключа нарушает поиск ранее сохранённых fingerprints.
- Доставка назначения и отзыва санкций по email подключена к transactional outbox:
  production использует SMTP, local — логирование. Ошибки отправки повторяются
  по retry policy outbox, удалённые получатели пропускаются. In-app inbox при
  блокировке намеренно недоступен. Интеграционные тесты используют mock sender;
  реальная доставка через production SMTP пока не проверена.
  SMTP допускает повторную доставку при сбое между отправкой и commit outbox;
  не обещать exactly-once для email.

## 8. Отложенная задача: рекомендации объявлений

Статус: обсуждение, реализация не начата. Задача оставлена следующему разработчику;
текущий этап — фиксация договорённостей, коммиты и push готового блока.
Не начинать реализацию рекомендаций без отдельного продолжения от пользователя.

Порядок работы согласован с пользователем:
1. Отдельный подход — обсудить и согласовать правила и контракт, без кода.
   После обсуждения остановиться и дождаться следующей команды.
2. Следующим подходом — реализовать согласованный вариант, проверить и обновить
   документацию. Не объединять оба подхода в один. Тесты запускать после
   логически завершённого блока, а не после каждой правки; при миграциях —
   полный suite согласно правилам проекта.

Исходные данные:
- Название позиции — свободная строка `TeamPosition.name` до 120 символов.
  Enum и каталога ролей нет; вводить их без согласования не нужно.
- Профиль и позиция используют общий каталог `Skill` через `ProfileSkill`
  и `TeamPositionSkill`. Уровней владения и разделения обязательных/желательных
  навыков сейчас нет. Отсутствие навыка в профиле не доказывает некомпетентность.
- Цель команды — текст `Team.purpose`; её нельзя напрямую сравнивать с каталогом
  целей профиля. Желаемые роли, формат проекта и доступное время пока не хранятся.
- Существующие рекомендации людей уже содержат объяснения и учёт показов.
  Переиспользовать подходы и подходящие сервисы, но не переносить формулу
  похожести людей на соответствие кандидата позиции без обоснования.

Предложение для обсуждения (не утверждённый алгоритм):
- Сначала рекомендации объявлений человеку; подбор кандидатов владельцу —
  отдельный последующий сценарий.
- Отбирать доступные OPEN объявления с будущим дедлайном и свободными позициями,
  соблюдая общие правила видимости, санкций, blocks и исключения команд читателя.
- Оценивать соответствие каждой свободной позиции по совпадениям навыков:
  учитывать количество совпадений и долю покрытых требований. Лишние навыки
  человека не должны снижать оценку. Веса и приоритеты ещё нужно согласовать;
  доля совпадений не является вероятностью совместимости.
- Оценку объявления брать по лучшей подходящей свободной позиции. Не повышать
  оценку лишь за количество позиций/объявлений команды; предусмотреть разнообразие.
- Показывать объяснение: подходящая позиция, совпавшие и недостающие навыки.
  Неполное совпадение пока предлагается использовать как мягкий сигнал,
  не как запрет на отклик.
- Пустые навыки профиля/позиции означают недостаток данных, не идеальное совпадение.
  Обсудить резервную выдачу свежих доступных объявлений, повторы показов, скрытия,
  уже отправленные отклики и последствия отклонений.
- Согласовать события для оценки качества: показы, открытия, скрытия, отклики,
  принятия и выходы. Ориентироваться на успешные вступления, не только клики.
  Обучаемое ранжирование и семантическое сравнение целей отложить до появления
  данных и измеримой потребности.
- Отдельно решить пагинацию и поведение при изменении профиля/выдачи.
  У поиска сейчас `page/size`; это не обязывает рекомендации использовать
  ту же модель, особенно при учёте показов и изменяемом ранжировании.
