## Как работаем

- Один проход — один этап ниже. Не объединять несколько этапов ради скорости.
  Если этап оказался велик, разделить его на подэтапы с отдельным результатом.
- После прохода остановиться: кратко описать изменения, выполненные проверки,
  оставшиеся риски и следующий шаг. Продолжать по команде пользователя.
- Перед правками смотреть git status и релевантный код. Сохранять чужие изменения,
  не коммитить и не пушить без просьбы. Не начинать реализацию в проходе планирования.
- Каждый этап оставляет компилируемый код. Промежуточные этапы не означают,
  что вся функция готова к использованию или выпуску.
- Тесты добавлять вместе с поведением, не откладывать их написание до финала.
  Дорогие прогоны группировать по контрольным точкам ниже.
- В конце этапа проверять diff, соответствие ТЗ, доступы, границы транзакций
  и затронутые сценарии. Для кода — compileTestJava; для чистой документации
  достаточно проверки diff и согласованности текста.
- Отмечать этап завершённым только при выполнении его критерия готовности.
  Невыполненную проверку явно записывать, не считать успешной по старому прогону.

## Политика прогонов

| Когда | Что запускать |
| --- | --- |
| Документация | Проверка diff и согласованности, без Gradle/Docker |
| Завершение небольшого этапа с кодом | compileTestJava и относящиеся к нему быстрые unit-тесты |
| A: после этапа 4 | Целевые интеграционные тесты отбора, карточек и видимости |
| B: после этапа 5 | Полный suite после миграции |
| B2: после этапа 6 | Целевые тесты запрета повторной подачи и существующего API откликов |
| C: после этапа 9 | Целевые тесты сессий, страниц, API и безопасности |
| D: после этапа 11 | Целевые тесты просмотров, cooldown и создания сессии |
| E: после этапа 13 | Целевые тесты cleanup, сквозных сценариев и гонок |
| После этапа 14 | Финальный полный suite |

Дополнительные миграции требуют полного suite после завершения соответствующего
логического блока согласно AGENTS.md. Падение проверки или изменение общего
security/существующего поведения может потребовать более раннего целевого прогона.
Успешные тяжёлые проверки не повторять без новых правок или конкретной причины.
Если Docker недоступен, явно фиксировать непроверенные сценарии и продолжать
независимую работу; не подменять интеграционную проверку одной компиляцией.
