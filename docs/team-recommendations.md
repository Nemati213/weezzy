## 1. Границы функции

Рекомендуем команды через доступные TeamRequest, объединяя объявления одной
команды в одну карточку. Пользователь выбирает свободную позицию и использует
существующий API TeamApplication. Принятие отклика по-прежнему атомарно добавляет
участника через TeamMemberService. Места не резервируются.

LIKE/PASS, скрытия, избранное, чёрные списки, рекомендации кандидатов владельцу,
семантическое сравнение текстов и обучаемая модель в этот блок не входят.
Листание не требует решения и не означает отказ пользователя от команды.

Рекомендации людей не изменять: их автоматическая запись показов при выдаче
и пустой ответ без signals не подходят новой ленте. Переиспользовать пакетную
загрузку профилей/фото, правила видимости и общий формат курсоров, где применимо.

## 2. Доступность и повторные отклики

Все endpoints требуют JWT; текущий user берётся только из principal.
Санкции текущего аккаунта проверяются на каждом запросе.
Как и поиск объявлений, просмотр доступен без активного/заполненного профиля:
если профиль отсутствует, навыки пусты; вступление требует обычных проверок
существующего API. Сессии и история принадлежат аккаунту, не публичному profileId.

В отбор входят только видимые по TeamVisibility команды и OPEN объявления
с recruitmentDeadline > now. Учитываются членство владельца, санкции и blocks.
Команды, где читатель состоит, исключаются. У позиции должно быть свободное место.
Участники карточки фильтруются по тем же правилам, что в карточке команды.

Правила относительно откликов действуют по паре кандидат + TeamPosition:

| Состояние | Рекомендации | Существующий API нового отклика |
| --- | --- | --- |
| Есть PENDING через любое объявление этой позиции | Позицию не предлагать | Существующий запрет дубликата внутри TeamRequestPosition не расширять |
| Есть DECLINED менее 24 часов назад | Позицию не предлагать | Запретить новый отклик на эту TeamPosition через любое объявление, 409 |
| После последнего DECLINED прошло 24 часа | Позиция снова допустима | Разрешить при выполнении остальных условий |
| WITHDRAWN, нет другого действующего запрета | Позиция снова допустима | Существующее поведение сохраняется |
| ACCEPTED и пользователь ещё в команде | Вся команда исключена | Существующий запрет повторного участия |
| Пользователь вышел/исключён после ACCEPTED | Обычный отбор и cooldown показов | Новый отклик допустим; старое ACCEPTED участие не восстанавливает |

24 часа считаются от максимального resolvedAt отклонённых откликов на позицию,
включая отклонения через закрытые/просроченные объявления. Граница разрешения:
now >= lastDeclinedAt + 24h. Отзыв другого отклика не сбрасывает срок.
Повтор идемпотентного decline не обновляет resolvedAt и не продлевает запрет.
Другие позиции этой команды не блокируются. Новая TeamPosition имеет другой ID.

Это единственное согласованное изменение общего flow откликов в данном блоке:
добавить проверку в TeamApplicationService.send после существующих блокировок
и проверок доступа, до вставки. Использовать порядок accounts → profiles → team
→ request/application; предусмотреть lookup/index по истории отклонений.
Существующий PENDING можно принять/отозвать/отклонить; прямые приглашения
и их принятие новым ограничением не затрагиваются.

Если все позиции исключены, команда не входит в новую сессию; в существующей
странице временно не возвращается. Это ограничение возможности отклика,
а не порог похожести. Оно не ослабляется при исчерпании остальных вариантов.

## 3. Ранжирование и объединение

Для каждой доступной TeamPosition вычислить:

- matchedCount = число общих уникальных Skill с профилем;
- requiredCount = число уникальных Skill позиции;
- coverage = matchedCount / requiredCount; при requiredCount=0 значение для
  сортировки 0. Ноль навыков не считается идеальным соответствием.

Порядок позиций: matchedCount DESC, coverage DESC, TeamPosition.createdAt ASC,
TeamPosition.id ASC. Долю сравнивать точно по числителю/знаменателю
(нулевой знаменатель нормализовать к 1), не по округлённому проценту.
UUID ASC означает порядок PostgreSQL UUID/канонической hex-строки;
учесть отличие от signed-сравнения половин UUID в Java.
Лишние навыки пользователя не штрафуются.
Навыки не разделены на обязательные/желательные; нехватка совпадений не запрещает
отклик и не является доказательством отсутствия квалификации.

Одну TeamPosition из нескольких объявлений представить одной опцией.
Выбирать доступное объявление с ближайшим будущим дедлайном, затем
TeamRequest.createdAt DESC, TeamRequest.id ASC. Возвращать его явный контекст
и TeamRequestPosition.id. После закрытия этого объявления при следующем чтении
можно выбрать другое доступное; прежний отправленный отклик не переносить.

Главная позиция — первая из доступных опций. Оценка команды — пара
matchedCount/coverage главной позиции. Для свежести команды взять максимальный
createdAt её доступных объявлений, публикующих хотя бы одну допустимую опцию.

На момент создания сессии команды разбиваются на две группы:

1. Вне cooldown (не показывались либо lastShownAt <= now - 3d): оценка DESC,
   свежесть DESC, teamId ASC. Нулевые совпадения тоже входят в эту группу.
2. Внутри cooldown: lastShownAt ASC, затем тот же порядок оценки/свежести/ID.

Сначала целиком первая группа, затем вторая. Нет жёсткого порога совпадений
и запрета показывать просмотренные команды после исчерпания остальных.
Количество позиций, объявлений и свободных мест не даёт отдельного бонуса.
При пустом профиле действует тот же порядок с нулевой оценкой.

Реализация прохода 11: после отбора уникальных доступных команд OrderService
загружает историю только для текущего userId и этих команд порциями до 500 ID.
Команды без истории или с lastShownAt <= now - impressionCooldown идут первыми
по прежнему ранжированию. Остальные сортируются по lastShownAt ASC, при равенстве
— по оценке, свежести и UUID. Порог берётся из app.team-recommendation.impression-cooldown;
3 дня — default. История не может вернуть команду, исключённую правилами видимости.
Чтение страниц и повтор clientRequestId не обращаются к истории для пересортировки.

Реализованная часть (проход 2): TeamPositionRanker.rank принимает Set навыков
профиля и коллекцию TeamPositionCandidate (positionId, createdAt, Set skillIds).
Кандидаты описывают позиции команды, а не ссылки объявлений. Отбор доступности
и объединение повторных публикаций выполняют сервисы отбора и сборки карточек.
Результат — неизменяемый список RankedTeamPosition с исходным кандидатом,
matchedSkillIds/unmatchedSkillIds, matchedCount()/requiredCount(). Первый элемент
задаёт главную позицию; отсутствие кандидатов возвращает пустой список.
Порядок команд, выбор объявления и cooldown в ранжировщик позиций не входят.

Реализованная часть (проход 3): TeamRecommendationCandidateRepository.findEligible
принимает optional profileId, captured now, границу недавних DECLINED,
afterRequestPositionId и порцию до 500. Вызывающие сервисы (порядок сессии)
сами проверяют аккаунт и получают profile; отдельной сервис-обёртки нет.
Возвращает компактные TeamRecommendationCandidate.
Поля: teamId, requestId, requestCreatedAt, recruitmentDeadline,
requestPositionId, teamPositionId, positionCreatedAt. Не возвращает entities.
Фильтры видимости/мест/членства/откликов выполняются в БД до LIMIT; навыки
не являются фильтром. Разные публикации позиции остаются отдельными строками
для этапа сборки; skill/history joins не размножают эти строки.

Внутренний порядок чтения — requestPositionId ASC как PostgreSQL UUID,
следующая порция использует ID последней прочитанной ссылки. Это обход кандидатов,
не порядок рекомендаций и не публичные курсоры сессии. Короткая/пустая порция
означает конец обхода. Вызывающий слой передаёт один captured now всем порциям;
согласованный снимок между запросами обеспечивает будущая внешняя транзакция
создания сессии REPEATABLE_READ. Сам метод отбора — readOnly, сессий не создаёт.
Порог DECLINED вычисляется из TeamApplicationProperties.reapplicationCooldown
(24h по умолчанию). В проходе 6 та же настройка подключена к существующему API
отправки: MAX(resolvedAt) по кандидату и TeamPosition проверяется после блокировок
и обычных проверок доступа/мест, до вставки. Время проверки и решения берётся
через Clock; повтор decline возвращает прежний результат без сдвига срока.
Запрет не применяется к принятию существующего PENDING или прямого приглашения.

Реализованная часть (проход 4): TeamRecommendationService.findForUser
принимает внутренние userId, список до 50 teamIds и captured now. Возвращает
карточки в переданном порядке, без повторов; недоступные команды/опции пропускает.
Каждое чтение заново отбирает ссылки объявлений, выбирает одну публикацию
на TeamPosition и ранжирует позиции по текущим навыкам. Карточка содержит
team, recommendedTeamPositionId и options; entryId добавит слой сессий.
Участники фильтруются общим с обычной карточкой TeamMemberVisibilityService,
позиции/места/навыки и READY-фото загружаются пакетно. DTO не содержат контактов.
Сборщик readOnly, не создаёт сессий и не фиксирует показы. Контрольная точка A
проверила его на PostgreSQL вместе с отбором и существующими API команд.

## 4. Серверная сессия

Для MVP полностью фиксировать порядок ID всех допустимых команд при создании,
включая резервную группу внутри cooldown. Не обрезать список до top-N с ложным
сообщением об исчерпании вариантов. Сохранять компактные записи PostgreSQL,
а не полные карточки, фотографии или копии профилей.

Создание использует один captured now и согласованный снимок данных
(REPEATABLE_READ для транзакции создания). Запись сессии и порядка атомарна:
читатель не видит частично сформированную ленту. Обрабатывать компактные
кандидатные данные пакетно/в БД; не загружать все полные карточки в память.
Переход к порционному формированию при необходимости — отдельное решение,
не незаметное изменение стабильности ленты.

Замер этапа 14 (`gradlew volumeTest`, TeamRecommendationVolumeTests, PostgreSQL 17
в Testcontainers): 4000 команд, из них 3000 с открытым объявлением и 6000 опций,
2000 участников, 1 млн строк истории, 200 истёкших сессий по 3000 записей.

| Операция | Результат |
| --- | --- |
| Создание сессии на 3000 команд, прогретое | ~0,8 с, включая вытеснение 11-й |
| Запись сессии | ~268 байт на запись с индексами, ~0,8 МБ на сессию |
| Чтение страницы 20 команд | 85–110 мс, 15 SQL, постоянно по страницам |
| Показ 20 записей | ~60 мс |
| Cleanup пакета 5000 / 20 000 | ~100 / ~180 мс |

Записи сессий и история ни в одном сценарии не читаются полным проходом.
Чтение страницы делает не более одного прохода по team_requests: это выбор
планировщика для hash join на малой таблице (~0,6 мс), индекс по team_id есть.
Известное ограничение: отбор при создании читает keyset-порции по 500, и каждая
порция заново вычисляет полный join видимости (~50 мс независимо от размера
порции). Стоимость растёт как N²/500: 3000 команд — 13 порций, ~0,65 с из 0,8 с.
Для каталога ITMO это приемлемо. При десятках тысяч открытых команд заменить
порции одним потоковым запросом (fetch size) с той же группировкой в Java.

Сессия содержит UUID, ownerUserId, clientRequestId, createdAt, expiresAt,
фиксированный pageSize и число записей. Запись содержит entryId, ordinal,
teamId, firstDeliveredAt и firstShownAt (последние nullable).
Уникальны (sessionId, ordinal), (sessionId, teamId), (ownerUserId, clientRequestId).
Ordinal неизменяем; удаление команды оставляет пустое место в порядке до cleanup,
без сохранения её личных данных. Отдельная история хранит lastShownAt
по (ownerUserId, teamId), обновляемый монотонно.

TTL сессии — 24 часа от создания, без продления чтением. Обновление ленты создаёт
новую сессию; старые курсоры действуют до её истечения. Для ограничения хранения
держать максимум 10 неистёкших сессий аккаунта: успешное создание 11-й удаляет
самую старую (createdAt ASC, id ASC). Делать это атомарно и конкурентно безопасно.
Таким образом, 24 часа — максимальный срок, а не обещание хранить бесконечное
число лент. История показов от удаления сессии не сбрасывается.

Повтор POST с тем же clientRequestId не создаёт вторую сессию и не вытесняет старые.
Ключ относится к сроку жизни сохранённой сессии; после удаления записи дедупликация
не обещается. Клиент генерирует новый UUID только для нового обновления ленты,
а для сетевого повтора переиспользует прежний.

Команды, которых не было в исходном снимке, появятся только в новой сессии.
У существующих записей данные актуальны: новые доступные позиции/объявления могут
появиться в карточке, недоступные исчезают. Состав, фото, места и объяснения
собираются заново. Навыки профиля берутся актуальные: главная позиция/объяснение
могут измениться, но порядок команд не пересчитывается до новой сессии.

Хранение прохода 5 (V51):

- team_recommendation_sessions: owner_user_id, client_request_id, created_at,
  expires_at, page_size (1–50), entry_count (>=0). Уникальный ключ повторного
  запроса действует в пределах аккаунта; expires_at строго позже created_at.
- team_recommendation_entries: id, session_id, ordinal (>=0), nullable team_id,
  first_delivered_at, first_shown_at. Ordinal начинается с 0. Уникальны пары
  session_id/ordinal и session_id/team_id; показ требует предыдущей выдачи
  и не может быть раньше неё. После удаления команды team_id становится NULL,
  запись/ordinal и исходный entry_count сохраняются, включая несколько таких
  пустых мест в одной сессии. Удаление сессии каскадно удаляет записи.
- team_recommendation_impressions: составной PK owner_user_id/team_id и
  last_shown_at. Upsert использует GREATEST, поэтому более старое событие
  не отодвигает историю назад. Сессия не является владельцем этой таблицы.
  Удаление команды удаляет её историю; удаление аккаунта удаляет его историю,
  сессии и все записи сессий через внешние ключи PostgreSQL.
- Индексы поддерживают ключ повторного запроса, окна ordinal, удаление команд,
  порядок вытеснения сессий, сроки очистки и cooldown аккаунта. Частичный индекс
  team_applications(applicant_profile_id, position_id, resolved_at DESC)
  WHERE status='DECLINED' вместе с индексом ссылок по team_position_id обслуживает
  поиск отказов через все объявления позиции без копирования бизнес-истории.

Entities хранят UUID, без JPA-графов аккаунта/команды и коллекции записей сессии.
Чтение окна и истории пакетное; сборка вложенных DTO выполняется отдельно через
TeamRecommendationService. Это предотвращает скрытые загрузки на каждую запись;
стоимость полной сессии на объёме измерена на этапе 14 (см. выше).
Таблицы и настройки сами не запускают API, запись показов или cleanup.
Проверено в точке B: миграция V50 → V51, ограничения/удаления, JPA validate,
монотонность истории и два запроса для окна/истории при 1 и 20 записях.

Создание прохода 7: TeamRecommendationSessionService.createForUser принимает
внутренние userId, clientRequestId и pageSize (1–50). Возвращает метаданные
TeamRecommendationSessionResult и created, чтобы будущий HTTP-слой различал
создание и сетевой повтор. Повтор действующей сессии сохраняет ID, порядок,
срок и размер; другой pageSize даёт conflict. Сохранённый истёкший ключ даёт
404, а после физического удаления строки ключ может быть использован заново.

TeamRecommendationSessionCreator выполняет попытку в новой транзакции
REPEATABLE_READ. Первая операция UPDATE users SET id=id блокирует строку
владельца и создаёт новую версию строки PostgreSQL, не меняя её значения.
Это важно: обычный SELECT FOR UPDATE сам не обновляет снимок ожидающей
REPEATABLE_READ-транзакции. Изменение версии заставляет конкурирующее создание
с устаревшим снимком завершиться конфликтом и повториться со свежим снимком.
Внешний сервис допускает до трёх попыток при TransientDataAccessException;
бизнес-ошибки не повторяются, исчерпанная ошибка не маскируется пустой лентой.
Вызывать внешний сервис нужно вне существующей транзакции (Propagation.NEVER).

После сериализации проверяются санкции и повтор ключа. Один captured now
в пределах успешной попытки используется при отборе, создании и вытеснении;
метаданные времени нормализуются к микросекундам PostgreSQL.
TeamRecommendationOrderService читает общую выборку кандидатов по 500 ссылок
с keyset-продолжением, навыки профиля один раз, пары positionId/skillId пакетно.
В памяти между пакетами остаётся одна оценка и свежесть на команду, без графа
команд, участников и фотографий. Повтор позиции в разных пакетах не даёт бонуса.
Внутри пакета используется TeamPositionRanker; команды сортируются по числу
совпадений, точной доле, свежести и UUID. Проход 11 добавляет приоритет вне cooldown
и порядок по давности показа для оставшихся команд.

Session сохраняется с готовым entryCount, entries записываются JDBC batch
порциями до 500 через TeamRecommendationSessionWriteRepository. До commit
удаляются самые старые ранее существовавшие активные сессии сверх лимита;
новая сессия сохраняется, даже если время создания совпало с прежними.
Запись сессии, всех ordinal и вытеснение входят в одну транзакцию PostgreSQL.
firstDeliveredAt/firstShownAt остаются NULL; создание не считается показом.
Чтение страниц, курсоры и публичные endpoints в этот проход не входят.

## 5. Страницы и курсоры

Реализация прохода 8: TeamRecommendationPageService.findForUser читает одно
фиксированное окно и вызывает TeamRecommendationService один раз для его ID
(до 50). Сборщик возвращает TeamRecommendation без привязки к сессии; сервис
страниц добавляет стабильный entryId в плоский TeamRecommendationResponse.
TeamRecommendationPageResponse содержит метаданные сессии, items и три курсора.
HTTP подключён через TeamRecommendationController в проходе 9.

В write-транзакции сначала проверяются санкции, затем блокируется строка
сессии с условием владельца. TTL проверяется по Clock после получения блокировки,
чтобы ожидание не позволило прочитать уже истёкшую сессию. Блокировка сессии
сохраняется до окончания сборки и записи выдачи; вытеснение/удаление ждёт commit.
Только возвращённые entry получают firstDeliveredAt одним условным UPDATE,
повторная выдача эту дату не меняет. firstShownAt и история показов не изменяются.
Параллельные чтения одной сессии последовательно проходят эту транзакцию.

Страница — фиксированное окно ordinal длиной pageSize, а не новый поиск.
Размер выбирается при создании: по умолчанию 20, допустимо 1–50; дальше неизменяем.
Курсор непрозрачен для клиента, содержит версию/тип, sessionId и начало окна.
Использовать отдельный тип в CursorTokenCodec; проверить длину (до 512 символов),
UUID, диапазон, выравнивание начала окна и соответствие sessionId в пути.
Пустой переданный cursor — 400; отсутствие параметра означает первую страницу.

Общий codec — Base64, не подпись и не авторизация. Даже корректно сконструированный
курсор не даёт чужую сессию: владелец проверяется из JWT перед чтением данных.
Клиенту разрешено читать любое корректное окно собственной действующей сессии.
Курсоры не содержат контактов, оценки или навыков. TeamRecommendationCursorCodec
использует тип team-recommendation-page и общую версию v1; UUID проверяется
в полном формате, ordinal — неотрицательный int без знака и ведущих нулей.
Неверный курсор проверяется после владельца и TTL: чужая или истёкшая сессия
остаётся 404 независимо от содержимого cursor.

На каждом чтении повторно проверить санкции читателя, видимость команды,
членство, объявления, места, PENDING и запрет после DECLINED.
Недоступные карточки пропускать; соседними записями из другого окна не заполнять.
Окна и курсоры остаются стабильны. Для каждого ответа возвращать pageCursor
(повтор текущего окна), nextCursor и previousCursor; отсутствующий сосед — null.
Внутри страницы порядок всегда прямой, в том числе при движении назад.

Пустой items при ненулевом nextCursor не означает конец: фронт продолжает
в том же направлении через пустые окна. Запрос ограничен одним окном;
сервер не сканирует всю оставшуюся сессию, пытаясь заполнить страницу.
previousCursor строится симметрично. Всегда двигаться по курсору ответа,
не запрашивать снова тот же пустой участок. Конец направления — null курсор.
Если команда вновь доступна, она может вернуться в своё прежнее окно.

Новая полностью пустая сессия возвращает items=[] и оба соседних курсора null.
У неё есть pageCursor первого окна для повторного чтения, но новые команды
потребуют обновления ленты. Не возвращать totalElements как актуальное число
видимых команд: фиксированный снимок и текущая доступность могут различаться.

Клиент хранит sessionId, pageCursor текущего окна, entryId текущей карточки
и положение прокрутки. Достаточно кеша нескольких страниц, не всей истории.
Возвращение из профиля не создаёт новую сессию. После потери кеша страницу
получают повторно; при 404 сессии фронт предлагает обновить подборку.
При исчезновении текущей карточки выбрать следующую доступную в направлении
движения. Восстановление означает прежние окна/порядок, не устаревшее содержимое.

## 6. HTTP API

Базовый путь: /api/team-recommendations/me/sessions.

POST создания и GET страницы реализованы в проходе 9, POST impressions —
в проходе 10. Все три метода требуют JWT и получают
владельца только из JwtAuthenticatedUser. Успешные ответы имеют Cache-Control:
no-store, private. Вступление по-прежнему использует API откликов.

| Метод | Путь относительно базового | Запрос | Ответ |
| --- | --- | --- | --- |
| POST | пустой | CreateTeamRecommendationSessionRequest | 201, Location и первая страница; повтор ключа — 200 |
| GET | /{sessionId} | необязательный cursor | 200, TeamRecommendationPageResponse |
| POST | /{sessionId}/impressions | RecordTeamRecommendationImpressionsRequest | 204 |

Создание:

```json
{
  "clientRequestId": "00000000-0000-4000-8000-000000000001",
  "pageSize": 20
}
```

clientRequestId обязателен. Отсутствующий или null pageSize получает default 20; неверный
размер — 400, без молчаливого clamp. Повтор ключа с другим размером — 409.
Повтор существующей истёкшей сессии — 404, без автоматического создания новой.
POST возвращает первую страницу с актуальным содержимым, не байтовую копию
первоначального ответа. DateTime соответствует принятому в проекте LocalDateTime.

Location содержит /api/team-recommendations/me/sessions/{sessionId} и при 201,
и при повторе с 200. Создание/поиск по ключу и чтение первой страницы — отдельные
транзакции: сохранённая сессия остаётся доступна для повтора, если ответ не дошёл.
Перед выдачей первой страницы снова проверяются владелец, TTL и доступность.
Если между созданием и чтением сессию удалили/вытеснили или истёк её TTL,
POST возвращает 404; не создаёт другую сессию незаметно для клиента.

TeamRecommendationPageResponse:

- sessionId, createdAt, expiresAt, pageSize;
- items: список TeamRecommendationResponse;
- pageCursor, nextCursor, previousCursor.

TeamRecommendationResponse:

- entryId: идентификатор записи сессии для учёта показа;
- team: id, name, purpose, description, ownerProfileId,
  members (существующий TeamMemberResponse);
- recommendedTeamPositionId: ID главной позиции, обязательно присутствует в options;
- options: непустой список TeamRecommendationPositionResponse в порядке раздела 3.

TeamRecommendationPositionResponse:

- request: id, title, description, recruitmentDeadline выбранного объявления;
- position: существующий TeamRequestPositionResponse (id — позиция объявления,

- matchedSkillIds, unmatchedSkillIds: непересекающиеся списки, покрывающие skills
  позиции; порядок по UUID ASC. Не возвращать числовой «процент совместимости».

members содержит profileId/displayName/positionId/positionName/joinedAt/photos;
photos использует ProfilePhotoResponse с ограниченным сроком downloadUrl.
Новый тип team не копирует весь TeamResponse с неподходящими для отклика позициями.
Карточка без options пропускается; recommendedTeamPositionId не бывает null.
Email, Telegram, userId и clientRequestId в карточках отсутствуют.

## 7. Учёт показов

Реализация: TeamRecommendationImpressionService.recordForUser. Проверяет весь
пакет до записи; повторы уже показанных entries не обновляют историю. Доступность
проверяется компактным SELECT DISTINCT team.id с общим eligibility кандидатов,
без сборки DTO, навыков, участников и медиа. При наличии хотя бы одной доступной
опции команда ещё может учитываться; сохранённой копии выбранной позиции нет.

Порядок блокировок: аккаунт через AccountProfileLockService, строка сессии,
существующие ключи команд по UUID через FOR KEY SHARE. Чтение/удаление сессии
и события одного аккаунта сериализуются; удаление команды не обрывает запись
истории по FK. После ожидания блокировок повторно проверяется TTL. Физически
удалённые команды пропускаются, включая удаление между чтением entries и блокировкой.
Успешные события разных сессий учитываются независимо.

TeamRecommendationImpressionWriteRepository перед записью нового показа обновляет
версию уже заблокированной строки аккаунта через UPDATE users SET id=id.
Ожидающий создатель REPEATABLE_READ получает конфликт сериализации и повторяет
попытку с актуальным снимком истории. Если показ откатился, обновление версии
и история тоже откатываются. Повтор уже учтённого entry не выполняет эту запись.

Затем одним JDBC CTE обновляет только
firstShownAt IS NULL и записывает историю из RETURNING. Оба изменения входят
в общую транзакцию. История использует GREATEST; при откате часов firstShownAt
также ограничен снизу firstDeliveredAt. Повтор не продлевает дату.
Эта история применяется к порядку новой сессии с прохода 11.

```json
{
  "entryIds": ["00000000-0000-4000-8000-000000000011"]
}
```

Непустой список 1–50 различных UUID, дубли внутри тела — 400.
Один запрос может охватывать несколько
страниц своей сессии. Сервер не принимает timestamp/userId/teamId от клиента.
Проверить владельца и срок сессии, существование всех entryIds в ней и
firstDeliveredAt: запись должна ранее входить в сформированный ответ с карточкой.
Чужая/неизвестная/невыданная запись — 404; пакет атомарен, без частичной записи.

firstDeliveredAt выставляется при подготовке успешного ответа только возвращённым
карточкам. Это не доказательство получения ответа или фактической видимости.
GET может обновлять эту служебную отметку, но не firstShownAt/lastShownAt.
Рекомендационные ответы не должны обслуживаться общим HTTP-кешем: Cache-Control
private, no-store; приложение может хранить их в своём ограниченном кеше.

Для будущего фронта критерий: карточка видна не менее чем на 50% в течение
непрерывной 1 секунды, экран активен. Отправлять после выполнения критерия,
не при скачивании. Сервер доверяет этому событию как аналитическому сигналу,
проверяет происхождение записи, но физическую видимость экрана не доказывает.

При первом событии записать серверное now как firstShownAt и обновить историю
lastShownAt = max(lastShownAt, now). Повтор entryId в той же сессии — 204 без
изменений. Одновременные повторы не продлевают cooldown. Просмотр в другой
сессии — новое событие. Задержанный показ уже недоступной команды/позиции
пропускается с 204; невидимые данные не раскрывать.

Смена навыков, отзыв отклика, отклонение и удаление сессии не сбрасывают историю.
Удаление аккаунта удаляет принадлежащие ему сессии/историю; повторная регистрация
не требует сохранять рекомендации удалённого аккаунта. Бизнес-санкции независимы.

## 8. Ошибки, сроки и очистка

Использовать ApiErrorResponse и существующую иерархию бизнес-исключений.
Новые общие поля ошибок и формат существующих endpoints не менять.

| Код | Ситуация |
| --- | --- |
| 400 | Неверные UUID/размеры/список показов/курсор, несовместимый с путём курсор |
| 401 | JWT отсутствует/недействителен |
| 403 | Аккаунту запрещён доступ действующей санкцией |
| 404 | Сессия неизвестна, чужая, истекла или удалена; запись показа не принадлежит выданной части |
| 409 | clientRequestId повторён с другим pageSize; новый отклик раньше срока после DECLINED |

Не различать для клиента чужую и неизвестную сессию. Проверить владельца до
выдачи сведений о её страницах. Не превращать ошибку БД/сервера в пустую ленту.
Для ошибки повторного отклика сообщение содержит время окончания запрета,
но клиент не должен разбирать текст как машинный контракт. Рекомендации
до окончания срока эту позицию не предлагают.

Namespace конфигурации ленты: app.team-recommendation. Ограничение повторных
откликов относится к домену откликов и задаётся отдельно через
app.team.application.reapplication-cooldown, независимо от использования ленты.

| Настройка | Значение MVP |
| --- | --- |
| impression-cooldown | 3 дня, мягкий |
| session-ttl | 24 часа от создания |
| impression-retention | 30 дней с последнего показа |
| app.team.application.reapplication-cooldown | 24 часа после отказа на ту же TeamPosition, жёсткий |
| max-active-sessions-per-user | 10, вытеснение самой старой при успешном создании новой |
| cleanup.enabled | true, включает фоновое расписание |
| cleanup.interval | 15 минут |
| cleanup.batch-size / max-batches-per-run | 5000 / 20 |

pageSize 20 (1–50) и максимум 50 entryIds — ограничения API.
Проверять положительность сроков/лимитов, retention >= session-ttl и
retention >= impression-cooldown. Время брать через внедряемый источник времени
для тестов, сохраняя LocalDateTime как в проекте. При t=expiresAt сессия уже 404,
не зависит от того, успел ли cleanup физически её удалить.

Cleanup удаляет сессии с expiresAt <= now и историю с lastShownAt строго раньше
now - impression-retention. История на точной границе сохраняется. Время и граница
retention фиксируются один раз на запуск через Clock. Удаление сессии не удаляет
свежую историю показов; firstShownAt активных сессий остаётся для дедупликации.
История DECLINED остаётся существующей бизнес-историей откликов: cleanup
рекомендаций не удаляет её и не сбрасывает ограничение повторной подачи.

Каждый пакет выполняется в отдельной транзакции. Лимит batch-size применяется
отдельно к заблокированным сессиям, удаляемым записям и строкам истории.
Сначала блокируются истёкшие сессии, затем удаляется ограниченное число их записей;
родитель удаляется только без оставшихся записей. Поэтому большая сессия может
очищаться несколько запусков, без неограниченного каскадного удаления.
Она уже недоступна через API по TTL, частично очищенная лента не возвращается.

Все выборки для удаления используют FOR UPDATE SKIP LOCKED. Несколько экземпляров
обрабатывают разные доступные строки. Занятая чтением/показом сессия, запись или
обновляемая история пропускаются; cleanup не берёт блокировки аккаунтов/команд.
После захвата истории условие retention повторяется в DELETE. Новый показ может
сохранить свежую дату или заново создать историю после удаления старой строки.
Пакет без удалений завершает запуск; это может означать занятость строк,
следующий запуск повторит попытку. Остальные запуски ограничены max-batches-per-run.

По умолчанию один экземпляр за запуск удаляет не более 100 000 строк каждого вида
(до ~9,6 млн записей в сутки при интервале 15 минут). Каждая сессия хранит запись
на каждую доступную команду, поэтому пропускная способность очистки должна
превышать поток создания: прежние 500 × 10 (480 тыс./сутки) не покрывали даже
сотни активных пользователей при тысяче команд. Замер этапа 14: пакет 5000 записей
и 5000 строк истории — ~100 мс, 20 000 — ~180 мс, без полного прохода по таблицам.
Записи удаляются через LATERAL по каждой заблокированной сессии (индекс
session_id, ordinal) и ctid уже заблокированных строк, чтобы план не зависел
от доли истёкших записей в таблице.
Это лимит объёма, а не гарантия времени выполнения. После ошибки завершённые
пакеты сохраняются, текущий откатывается; scheduler сообщает об ошибке и повторит
очистку по следующему расписанию. Используются существующие индексы V51.

Переменные окружения: TEAM_RECOMMENDATION_CLEANUP_ENABLED,
TEAM_RECOMMENDATION_CLEANUP_INTERVAL, TEAM_RECOMMENDATION_CLEANUP_BATCH_SIZE,
TEAM_RECOMMENDATION_CLEANUP_MAX_BATCHES_PER_RUN. enabled=false выключает только
фоновое расписание; сервис остаётся доступен для явного вызова внутри приложения.
В Gradle tests расписание отключено, чтобы не мешать управляемому времени тестов.

Micrometer-метрики с префиксом weezzy.team.recommendation.cleanup:

- runs с outcome=success/failure — исход запуска, в том числе пустого;
- batches — число завершённых транзакций пакетов, включая пустой завершающий;
- deleted с kind=session/entry/impression — удаления только завершённых пакетов;
- duration — время запуска, включая неуспешный.

При эксплуатации следить за ошибками, длительностью и ростом просроченных данных.
Если запуски постоянно исчерпывают бюджет пакетов, а очередь растёт, подбирать
интервал/лимиты по нагрузке БД. Логи успешных удалений содержат количества каждого
вида; метрики не доказывают отсутствие очереди. SQL и конкурентные сценарии
cleanup проверены в точке E, стоимость пакетов — нагрузочным тестом этапа 14.

## 9. Проверяемые сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Java/Spring/PostgreSQL против позиций с 3/4, 2/2, 1/3 совпадениями | Порядок 3/4 → 2/2 → 1/3 |
| Лишние навыки в профиле | Оценка не уменьшается |
| Нет навыков/совпадений | Доступные команды всё равно попадают в ленту |
| Подходящая команда в cooldown, неподходящая вне cooldown | Сначала вне cooldown, затем просмотренная |
| Одна команда, несколько объявлений одной позиции | Одна карточка и одна опция, ID для отклика однозначен |
| Отклик PENDING через другое объявление той же позиции | Эту позицию не предлагать; остальные опции сохраняются |
| Отказ 23ч59м назад, попытка через другое объявление | Позиция исключена; прямой POST отклика — 409 |
| Ровно 24 часа после последнего отказа | Ограничение снимается; обычные проверки остаются |
| Отказ по backend, отклик на design той же команды | Отказ не блокирует design |
| Отзыв другого отклика после отказа | Не отменяет ещё действующий 24-часовой запрет |
| Владелец повторил decline того же отклика | Срок запрета не сдвигается |
| Пролистал пять/двести карточек назад | Те же окна и порядок действующей сессии |
| Клиент выгрузил старые страницы | Восстановление по sessionId + pageCursor |
| Заполнились все позиции в окне | items=[]; соседние курсоры остаются, если окна существуют |
| Новая команда появилась после создания | Только новая сессия; существующий порядок не меняется |
| Поменялись навыки пользователя | Текущие объяснения/главная опция обновляются, порядок команд прежний |
| Объявление главной опции закрыто, есть другое | При чтении выбирается доступная ссылка; старый отклик не переносится |
| Читатель вступил в команду | Карточка пропускается при следующем чтении |
| Архив/blocks/санкции владельца | Новое чтение не раскрывает команду; участники также фильтруются |
| Предзагрузка страницы | firstDeliveredAt возможен, cooldown не меняется |
| Возврат назад и повтор события показа | 204, срок не продлевается в этой сессии |
| Две конкурентные отправки одного показа | Один учтённый показ, монотонная история |
| Сетевой повтор создания | Та же сессия; 200, актуальная первая страница |
| Истекла/вытеснена сессия | 404, новая лента только по явному POST |
| Последнее место занято приглашением после выдачи | Обычный API отклика/принятия не превышает capacity |

Изменение видимости уже скачанного клиентского кеша невозможно отозвать задним
числом. Сервер проверяет каждое новое чтение/действие; фронт перечитывает страницу
при возврате из долгого фона и обрабатывает отказ доступа к профилю/отклику.
Наличие карточки никогда не обещает сохранение свободного места.
