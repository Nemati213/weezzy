# Команда под цель, позиции и набор

Команда создаётся под конкретную цель: проект, хакатон, соревнование.
Цель хранится в обязательном `Team.purpose`. Общие постоянные чаты
не являются частью этой модели. Когда работа закончена, команду можно
архивировать с сохранением состава и истории.

## Состав и позиции

`TeamPosition` принадлежит команде, содержит название роли, описание,
вместимость `capacity` и связи с существующим каталогом `Skill`.
Каждый `TeamMember`, включая основателя, обязательно занимает позицию
своей команды. Права владельца определяются отдельно через
`ownerProfileId`: «владелец» не заменяет профессиональную роль.

При создании команды основатель указывает `purpose` и `ownerPositionName`.
Для него создаётся занятая позиция вместимостью 1 в той же транзакции.
Владелец может добавить позиции, изменить их название, описание, навыки
и вместимость. Вместимость нельзя уменьшить ниже текущего числа участников.

- `filledSlotsCount` — число текущих участников на позиции.
- `remainingSlotsCount = capacity - filledSlotsCount`.
- Приглашения и отклики в ожидании не резервируют место.
- Выход или исключение освобождает место, сохраняя историю решений.
- Повтор принятого решения не восстанавливает вышедшего участника.
- Удаление позиций и перевод участников между позициями пока не реализованы.

Карточка команды возвращает цель, позиции и позицию каждого доступного
участника. Контактные данные и внутренний user ID не раскрываются.

## Объявление о наборе

`TeamRequest` — объявление о наборе в уже определённые позиции команды.
У него свои заголовок, описание, дедлайн и статус `OPEN/CLOSED`.
Создание принимает непустой набор `positionIds` существующих позиций
этой команды; каждая должна иметь свободное место.

`TeamRequestPosition` теперь только связывает объявление и `TeamPosition`.
Одна позиция может публиковаться в нескольких объявлениях. Вместимость
у неё общая: объявления не создают дополнительные места.
Редактирование позиции отражается во всех объявлениях, включая историю.

Отдельный `targetTeamSize` удалён. `availableTeamSlotsCount` равен сумме
свободных мест в позициях конкретного объявления. Эти значения нельзя
суммировать между объявлениями, если они публикуют одни и те же позиции.

Закрытие объявления или истечение его дедлайна запрещает новые отклики
и принятие по нему. Состав и позиции команды сохраняются; прямое приглашение
на свободную позицию активной команды остаётся доступно.
Просроченное объявление автоматически не меняет статус.

## Два способа вступления

Приглашение отправляет владелец конкретному кандидату на `TeamPosition`;
принимает или отклоняет кандидат, отменяет отправитель.
Отклик отправляет кандидат через позицию объявления; принимает или отклоняет
владелец, отзывает кандидат.

Оба способа используют `TeamMemberService.ensureCanJoin/add`:
проверяются активность команды и профилей, санкции, blocks, принадлежность
позиции команде, отсутствие участия и свободное место. Отклик дополнительно
требует открытого объявления с будущим дедлайном.

Принятие атомарно добавляет участника с позицией, сохраняет решение и outbox.
Два одновременных принятия на последнее место, в том числе через разные
объявления или приглашение и отклик, не могут превысить вместимость.

Отклики имеют статусы `PENDING/ACCEPTED/DECLINED/WITHDRAWN`.
Допускается один ожидающий отклик профиля на одну запись позиции объявления.
Разные позиции и разные объявления допускают отдельные отклики.
У приглашений сохраняется одно ожидающее приглашение на пару команда/кандидат.
Несовместимое повторное решение возвращает conflict; повтор того же решения
идемпотентен.

Отзыв и отклонение доступны сторонам после закрытия объявления, дедлайна
или архивирования. Blocks и неактивный профиль не мешают завершить ожидающее
решение; санкции аккаунта действующего пользователя продолжают действовать.
История отклика доступна только его сторонам.

## API

Все методы требуют JWT. Текущий пользователь определяется из JWT.

Создание команды: `POST /api/teams`.

```json
{
  "name": "Hackathon team",
  "description": "Сервис для студентов",
  "purpose": "Собрать прототип для осеннего хакатона",
  "ownerPositionName": "Backend developer"
}
```

Позиции: `POST/GET /api/teams/{teamId}/positions`,
`GET/PUT /api/teams/{teamId}/positions/{positionId}`.
Запись разрешена только владельцу активной команды с активным профилем.
Чтение использует общую видимость команды: активность владельца, санкции,
blocks. Тело создания и редактирования:

```json
{
  "name": "Designer",
  "description": "Интерфейсы прототипа",
  "capacity": 2,
  "skillIds": []
}
```

Создание набора: `POST /api/teams/{teamId}/requests`.

```json
{
  "title": "Ищем дизайнера",
  "description": "Собираемся к осеннему хакатону",
  "recruitmentDeadline": "2027-09-01T18:00:00",
  "positionIds": ["UUID позиции команды"]
}
```

Редактирование объявления принимает только `title`, `description`,
`recruitmentDeadline`. Состав публикуемых позиций сохраняется.
Остальные endpoints карточки, списка владельца и закрытия не изменились.

Приглашение: `POST /api/teams/{teamId}/invitations`,
тело `{"inviteeProfileId": "UUID кандидата", "positionId": "UUID позиции команды"}`.

Идентификаторы различаются:

- `TeamPositionResponse.id`, `TeamMemberResponse.positionId` и
  `TeamInvitationResponse.positionId` обозначают позицию команды.
- `TeamRequestPositionResponse.id` и `TeamApplicationResponse.positionId`
  обозначают запись позиции в объявлении.
- `teamPositionId` в этих двух ответах указывает исходную позицию команды.

| Метод | Путь | Действие |
| --- | --- | --- |
| POST | `/api/team-request-positions/{positionId}/applications` | Отклик через позицию объявления |
| GET | `/api/team-applications/me` | Свои отклики |
| GET | `/api/team-requests/{requestId}/applications` | Отклики объявления для владельца |
| GET | `/api/team-applications/{id}` | Карточка для сторон |
| POST | `/api/team-applications/{id}/accept` | Принять владельцем |
| POST | `/api/team-applications/{id}/decline` | Отклонить владельцем |
| POST | `/api/team-applications/{id}/withdraw` | Отозвать автором |

Тело отклика: `{"message": "Помогу с дизайном"}` или `{}`.
Сообщение необязательно, максимум 2000 символов.
Списки принимают `page`, `size` (1–100, по умолчанию 20), необязательный
`status`; список владельца также принимает `positionId` записи объявления.
Сортировка: `createdAt DESC, id ASC`. Без статуса возвращается вся история.

Создание возвращает 201 и Location; неверный ввод — 400, чужая карточка
отклика — 404, чужой список владельца — 403. Дубликат ожидающего решения,
занятое место, существующее участие и несовместимое решение — 409.

Это изменение контракта API: старые запросы создания команды без цели
и позиции основателя, приглашения без позиции и вложенные определения
позиций при создании объявления больше не поддерживаются.

## Поиск объявлений

`GET /api/team-requests` возвращает `PageResponse<TeamRequestResponse>`.
JWT обязателен; для просмотра не требуется созданный или активный профиль.
Санкции текущего аккаунта запрещают поиск.

Параметры:

- `query` — подстрока до 200 символов. Пробелы по краям удаляются,
  пустая строка означает отсутствие текстового фильтра. Регистр не учитывается;
  `%`, `_` и `!` ищутся буквально.
- `skillIds` — до 20 различных UUID навыков, параметр можно повторять.
  Все выбранные навыки должны входить в одну свободную публикуемую позицию.
  Неизвестный UUID даёт пустую выдачу, а неверный формат — 400.
- `sort=NEWEST` (по умолчанию) — `createdAt DESC, id ASC`;
  `sort=DEADLINE_ASC` — `recruitmentDeadline ASC, id ASC`.
- `page` от 0 и `size` от 1 до 100 (по умолчанию 20).

Текст ищется по заголовку и описанию объявления, названию и цели команды,
названию и описанию свободной позиции. Если одновременно указан фильтр навыков,
совпадение текста позиции и навыков должно относиться к одной позиции.
Совпадение текста самого объявления или команды подходит любой свободной
позиции с нужными навыками.

Выдаются только OPEN объявления с будущим дедлайном и свободной позицией.
Общие правила `TeamVisibility` используются и карточкой команды, и поиском:
активны команда и профиль владельца, у владельца есть аккаунт и членство,
нет действующей санкции владельца и blocks с читателем в любую сторону.
Команды, где читатель уже участник (включая собственные), исключаются из поиска;
доступ к их карточкам и списку владельца сохраняется.

Фильтрация выполняется в БД до LIMIT/OFFSET и подсчёта общего количества.
Несколько подходящих позиций не дублируют объявление. Ответ содержит обычную
карточку объявления со всеми его позициями; фильтры выбирают объявления,
а не урезают их состав. Отклик всё равно повторно проверяет доступность
и вместимость в момент отправки/принятия.

V50 добавляет частичный индекс для новых OPEN объявлений. Поиск по дедлайну,
навыкам и составу использует существующие индексы. Подстроковый текстовый поиск
не имеет отдельного индекса; его производительность на большом каталоге
потребует проверки на реальном объёме данных.

## Транзакции и сервисы

Порядок блокировок: accounts по ID, profiles по ID, team, затем
request/application либо invitation. Редактирование вместимости тоже
блокирует команду. Проверки доступности и мест выполняются после блокировок.

Профили используются через `ProfileService`, блокировки — через
`AccountProfileLockService`, права команды — через `TeamAccessService`,
объявления — через `TeamRequestService`, позиции — через `TeamPositionService`.
Вступление и подсчёт мест общие в `TeamMemberService`.
Контроллеры не содержат бизнес-логики.

## Уведомления

Новый отклик и отзыв уведомляют владельца команды.
Принятие/отклонение уведомляет кандидата. Уведомления приглашений сохранены.
Все события создаются через transactional outbox в транзакции действия;
`NotificationService.createIfAbsent` обеспечивает дедупликацию по source event.

Обработчики проверяют актуальность решения и доступность сторон.
Уведомление о новом отклике пропускается, если решение уже завершено,
набор недоступен или место занято. Уведомление о решении может прийти после
закрытия объявления/дедлайна. Отклонение и отзыв допускают архивную команду.
Удалённые получатели и устаревшие события пропускаются.

Payload отклика содержит applicationId, teamId, requestId, positionId,
teamPositionId, status. Payload приглашения дополнен positionId.
Email, Telegram и внутренний user ID не раскрываются.

## Миграции

V48 создаёт отклики и outbox-события.
V49 переносит позиции и навыки из объявлений в команду с сохранением ID,
переводит записи объявлений в ссылки, делает позицию обязательной для
участников и приглашений, удаляет target_team_size.
Составные внешние ключи запрещают участникам и приглашениям чужую позицию.

Для старых команд цель берётся из описания либо названия.
Участникам без позиции и старым приглашениям назначается техническая позиция
«Позиция не указана (перенос)»; неизвестная профессиональная роль не угадывается.
Её вместимость учитывает прежних участников без позиции и ожидающие приглашения.
Владелец может переименовать эту позицию. История откликов, приглашений
и уже назначенные позиции участников сохраняются.
